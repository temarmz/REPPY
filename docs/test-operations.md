# Разбор сбоев и остановка массового теста

Публикация и реальный Pages rollback: [отчёт](operations-publication-2026-11-07.md).

Результаты выполненных репетиций и границы проверки: [аудит 7 ноября](operations-audit-2026-11-07.md).

Ответственный во время каждой сессии — владелец репозитория. До старта он фиксирует время, окружение, release из `release.json` (в iOS — `REPPY_RELEASE` из журнала), число участников и предыдущий успешный deploy run/attempt. Во время теста оператор проверяет ошибки и задержки каждые 5 минут. Автоматический health-check раз в полчаса дополняет это наблюдение, но не заменяет его. Отсутствие жалоб не является измерением успешности.

## Что можно увидеть

В профиле обеих ролей и на экране восстановления есть «Скачать логи». Веб-экспорт v2 содержит release, время UTC, код операции, случайный `operationId`, результат, длительность и разрешённый код ошибки. HTTP-запрос дополнительно содержит `requestId` из ответа (`x-reppy-operation-id` у Edge Functions, иначе `sb-request-id`). `x-client-info` передаёт release и случайный ID HTTP-запроса. Повторы команды очереди сохраняют её ID; каждый HTTP-запрос имеет свой ID. Это разные уровни: журнал не обещает автоматическое дерево всех запросов одной бизнес-команды.

Экспорт iOS содержит версию, ID запроса, категорию API, длительность, HTTP status и серверный ID. Сетевой путь, параметры, тело и ошибки API в экспорт не попадают. CI передаёт уникальный `REPPY_RELEASE=ios-<SHA>-<run>-<attempt>`; при локальной раздаче сборки этот build setting тоже нужно задать. `development` не годится для массового теста.

Успешный медленный запрос сохраняется с длительностью. Веб пишет безопасное предупреждение при ошибке и длительности >5 секунд. Очередь веба отмечает незавершённую активную команду каждые 15 секунд, не запускает параллельную запись и не выдаёт её за успешно сохранённую. iOS отмечает запрос, который не завершился за 15 секунд. Edge wrapper пишет `PENDING` через 15 секунд, затем конечный HTTP status и длительность. Для определения текущего зависания берётся **последняя запись одного ID**, а не любое историческое событие pending. Таймеры в фоновой вкладке/iOS могут быть отложены системой.

Веб ограничивает один JSON-запрос 12 секундами, включая получение тела. Повторяемый прогресс может сделать до двух дополнительных попыток с backoff: общая команда способна занять дольше 12 секунд. Нативный JSON-запрос ограничен 30 секундами, upload — 120 секундами. Эти пределы защищают от ожидания без конца и не являются допустимыми задержками продукта. Upload/видео веба не входят в JSON-таймаут и текущие метрики.

Для серверного расследования: Supabase Dashboard → Edge Functions → Logs, искать JSON `event=server.request`, `function`, `clientRequestId`/`operationId`, `release`, status и durationMs. Для REST/Auth использовать серверный request ID и время в Supabase API/Auth/Postgres Logs. Потерянный ответ не даёт серверного ID: у Edge остаётся поиск по `clientRequestId`, у REST — время и категория запроса. Перед повтором спорной оплаты/завершения сверить серверный результат. Автоматически повторять денежные команды нельзя.

Клиентские журналы ограничены: веб — 200 событий операций и 500 действий, iOS — 200 операций и 500 действий текущего процесса. Это средство расследования конкретной жалобы, не централизованный сбор всех клиентских ошибок. Экспорт стоит получить сразу после сбоя; сетевые ошибки без ответа видны только на клиенте. Серверные журналы доступны в Supabase, срок их доступности зависит от тарифа. Сохранить обезличенную выдержку в закрытый протокол инцидента до её удаления.

Для локальной сводки одного экспорта: `npm run ops:metrics -- /path/reppy-activity-log.json [UTC-конец-окна]`. Команда считает последние результаты уникальных операций за 5 минут; p95 выводится только при ≥20 завершениях. Кольцевой экспорт может быть неполным и не заменяет серверную статистику всех участников. Для iOS длительность API — время транспорта; ожидание очереди нативных форм в эту метрику не входит.

## Данные в логах

Прикладные логи и экспорт содержат фиксированные коды, случайные идентификаторы, версию, время, status и длительность. Имена, телефоны, email, UUID аккаунтов/тренировок, текст заметок, упражнения/результаты, URL/query, тела, Authorization/apikey и сообщения/стеки исключений не записываются. Старый журнал сырых UI-ошибок удаляется при загрузке нового клиента. React root отключает стандартную печать перехваченных исключений; UI boundary пишет только код сбоя. Health-check больше не печатает `last_error` из outbox.

Это правило относится к коду REPPY. Инфраструктурные access-логи Supabase и содержимое самого backup — отдельные источники с отдельным доступом; не прикладывать их целиком к жалобе. Не включать запись HTTP-тел, заголовков авторизации и session replay в production. Не просить пользователя присылать токен, localStorage целиком или HAR. Диагностический JSON передавать ответственному по закрытому каналу.

## Допустимые задержки и стоп-условия

Начальные границы для теста, а не обещание SLA. Оценивать отдельно каждую сборку/платформу и операцию; окно — 5 минут, минимум 20 завершённых операций для процентилей/долей. На меньшей выборке фиксировать максимум и каждое зависание отдельно. Не смешивать полную загрузку большого аккаунта, RPC, видео и отрисовку экрана. Преднамеренные 409 в тесте гонок и искусственное отключение сети размечаются отдельно.

| Метрика | Допуск / действие |
| --- | --- |
| Обычный JSON API / RPC | p95 ≤2 с; два последовательных окна выше → остановить расширение нагрузки |
| Подтверждение записи, включая очередь/backoff | p95 ≤3 с; два окна выше → остановить расширение нагрузки |
| Полная загрузка аккаунта | p95 ≤5 с; два окна выше → остановить расширение нагрузки |
| Обычный переход по уже загруженным данным | p95 ≤1 с; два окна выше → остановить расширение нагрузки |
| Сохранение без конечного результата | 15 с → расследование; 60 с или два пользователя с таким сбоем → остановить тест |
| Неожиданные 5xx/таймауты | >1% при ≥20 запросах за окно либо 3 подряд на обычном сценарии → остановить тест |
| Telegram outbox | processing/pending старше 5 минут или исчерпание попыток → приостановить сценарии с уведомлениями |
| Потеря подтверждённых данных, двойное списание, доступ к чужим данным, секрет в логе | Один подтверждённый случай → немедленно остановить весь тест |
| Повторяемый краш/History API exception при обычных действиях | Остановить затронутую платформу, сохранить журнал и шаги |
| Нельзя получить диагностический журнал, нет проверенного backup или доступного rollback-артефакта | Не начинать следующую сессию |

При остановке: прекратить новые подключения и запись в затронутом сценарии, записать время/release/ID операции, сохранить диагностику, проверить серверный результат, выбрать исправление или откат. Не предлагать очистить данные/черновики как первый шаг. Возобновление — после воспроизведения причины, проверки исправления на изолированном окружении и одной контрольной сессии обеих ролей.

## Backup и проверка восстановления

Перед массовой сессией нужен завершённый backup **не старше 24 часов**, до релиза с миграциями — отдельная копия непосредственно перед изменениями. Еженедельный workflow сам по себе этого условия не выполняет: запустить `Backup production Supabase` вручную. Целевой RPO теста ≤24 ч; целевой RTO приложения после отката ≤15 мин, восстановления данных ≤60 мин. Это операционные цели; локальный короткий drill не доказывает hosted RTO.

Production workflow шифрует весь архив AES-256-GCM до загрузки artifact; без `PRODUCTION_BACKUP_ENCRYPTION_KEY` публикация backup завершается ошибкой. Локальная копия ключа находится в игнорируемой `.backups/operations-2026-11-07/backup-encryption-key` с правами 0600; её нужно сохранить отдельно от архивов в менеджере паролей. При утере ключа зашифрованные копии не восстановить.

`backup:create` теперь создаёт format v2: дополнительно `platform-hooks.sql` с триггером `on_auth_user_created` и четырьмя REPPY Storage policies. Стандартный dump их не включает, поскольку они прикреплены к управляемым схемам Auth/Storage. `backup:verify` проверяет наличие обязательных файлов и их SHA-256. Проверка v1 возможна для старых архивов, но для нового массового теста нужен v2. Сами Auth/Storage таблицы на hosted создаёт Supabase, их нельзя заменять самодельной схемой.

В основном deploy workflow локальный restore-drill добавлен после backend integration, WebKit operations и статический rollback-drill — в frontend checks. CI сохраняет отчёты; SQL dumps и backup с данными в эти диагностические artifacts не включаются.

Повторяемая локальная репетиция:

```sh
npm run supabase:start
npm run ops:restore-drill
```

Требуются Docker в PATH и локальный Supabase на 127.0.0.1:54321. Скрипт берёт ключи только из локального `supabase status`, создаёт синтетические записи и видео, делает настоящие CLI dumps и Storage export, проверяет SHA-256, восстанавливает backup в отдельном контейнере без сети. Сравнивает число строк всех включённых в data dump таблиц `public/private/auth/storage` (служебные миграционные таблицы и vector-таблицы CLI исключает), баланс, права владельца/постороннего тренера, новый профиль через Auth trigger, четыре Storage policies, перенос и SHA-256 байтов видео; намеренная порча файла должна быть отклонена. Тестовые записи и контейнер удаляются; отчёт остаётся в `work/ops-restore-*/report.json`. Перенос байтов в файловую папку не является проверкой загрузки видео через hosted Storage API.

Hosted restore проводить только в новый пустой проект: сначала официальная схема восстановления, затем `platform-hooks.sql` после `schema.sql`, данные одной транзакцией с `session_replication_role=replica`; восстановить объекты Storage через API, отдельно secrets и расписания Cron из миграций/операционной конфигурации. Проверить вход/создание профиля, обе роли/RLS, тренировку, баланс и чтение видео. Источник: [Supabase Backup and Restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Существующие hosted/local версии Auth могут различаться — локальный matching-platform drill не снимает эту границу. Не восстанавливать backup поверх production и не откатывать БД одновременно со статикой.

## Откат релиза

Deploy сохраняет `reppy-release-<run>-<attempt>` на 35 дней: готовая статика, `release.json`, манифест SHA-256. Нужен **успешный** запуск `deploy-pages.yml` с main. Workflow `Roll back Pages artifact` принимает run ID и attempt, скачивает именно тот архив, проверяет файлы и публикует исходные байты без npm install/сборки. Старые релизы до появления этих артефактов этим способом недоступны. Сохранять два успешных артефакта до начала массового теста.

После отката проверить `release.json` по URL приложения, свежую загрузку, вход обеих ролей, сохранение/чтение и сохранность черновика на прежнем устройстве. Уже открытые вкладки продолжат старый код до перезагрузки. Нативный установленный клиент не откатывается GitHub Pages: для него нужна предыдущая совместимая сборка и отдельная раздача. Любые изменения БД должны быть совместимы с обеими версиями; при несовместимой миграции этот путь закрыт, нужен forward fix/отдельный план данных.

```sh
npm run ops:rollback-drill
```

Локально создаёт два артефакта, переключает их на одном HTTP origin, удаляет распакованную предыдущую версию и восстанавливает её из tar. Проверяет SHA-256, release и сохранность localStorage демо. Отчёт — `work/ops-rollback/report.json`. Это репетиция статического отката; она не выполняет GitHub Pages deploy и не доказывает совместимость с будущими миграциями.

## Оставшаяся граница WebKit History API

Старый стресс-аудит зафиксировал исключение на >100 изменений за 10 с у установленного движка. В [текущем исходном коде WebKit](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/page/History.cpp) тоже указаны 100 изменений за 10 с, общие для push/replace в main frame. Это **не универсальная константа Safari**: [WebKit описывает также окно 30 с](https://bugs.webkit.org/show_bug.cgi?id=156115), а конкретная версия движка может менять ограничения.

Теперь одинаковый state не перезаписывается, непрерывная прокрутка хранит позицию в sessionStorage по записи history и маршруту, не вызывает replaceState каждый кадр. Состояние history фиксируется перед переходом; после reload/Back/Forward позиция доступна отдельно. Back закрывает подтверждение и обычные модальные окна без повторного открытия; возвращение фокуса проверяется отдельно.

Произвольно быстрые **настоящие** push/replace, модальные переходы и внешние hash-изменения по-прежнему могут исчерпать системную квоту. Ошибка журналируется без URL и повторно выбрасывается; фиктивное успешное переключение, очистка history и автоматический reload не применяются. Общий async throttle для всех переходов пока не введён: он менял бы порядок Back/Forward и защиту несохранённых форм. В стресс-прогоне сохраняется пауза 250 мс; успешный paced soak не выдаётся за исправление непейсированного предела.

```sh
npm run test:ops:web
```

Проверяет обе роли/темы, 160 кадров непрерывной прокрутки без History API writes и восстановление после reload в Chromium/WebKit, а также Back/Forward, грязные формы и модальные окна. Обычное действие, приводящее к SecurityError, является дефектом и стоп-условием, даже если синтетический непейсированный поток остаётся известной границей.
