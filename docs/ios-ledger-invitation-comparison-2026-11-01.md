# История абонемента и приглашения — 1 ноября 2026

Эталоны веба сняты в локальном демо, Chrome 393 × 852, обе темы, ru-RU, Europe/Moscow. Охват: история Артема, редактирование и добавление пополнения, приглашение, готовая ссылка и профиль неподключённого ученика. Нативный клиент использует тот же общий демо-контракт.

## Исправления

| Область | Было в iOS | Стало |
| --- | --- | --- |
| История | Раздельные большие карточки с повторяющимися подписями | Общий компактный список с тонкими разделителями, дельтой, деталями операции, датой и балансом после неё |
| Сводка | Маленький баланс отдельно от действия | Имя ученика над заголовком, общая карточка текущего баланса с основным действием пополнения |
| Оплата | Выпадающий способ оплаты, другие подписи и значения по умолчанию | Нативный сегмент «Наличные / Перевод», поля в одной строке с вертикальной адаптацией, счётчик комментария 240, ошибки возле полей, подписи как в вебе |
| Дата оплаты | Для даты без времени ISO-парсер возвращал nil и подставлялась сегодняшняя дата | Общий разбор календарной даты/ISO timestamp; редактирование старого пополнения сохраняет исходную дату. Сводка профиля и история используют один формат |
| Удаление абонемента | Кнопка без пояснения последствий | Отдельная зона, явно указано сохранение тренировок и результатов; нативное подтверждение |
| Приглашение | Ссылка и «Поделиться» внутри формы имени, срок действия не показывался | Экран готовой ссылки, срок из ответа backend, копирование, системное «Поделиться», завершение; черновик имени изолирован по аккаунту |
| Ожидающий ученик | Нельзя удалить из профиля | Удаление через существующий `delete_pending_student`, тот же RPC, что у веба. Активного ученика удалить этим действием нельзя; сервер разрешает гонку принятия/удаления под блокировкой |

Компоненты ConnectedList, LedgerSummary, PaymentMethodPicker, InvitationReady внесены в каталог и дизайн-кит. Divider экспортируется из семантического веб-токена. Пополнения/удаления по-прежнему проходят через существующие команды и проверки revision; серверные правила расчёта и RPC не менялись.

Рабочее приглашение создаётся только авторизованным тренером через существующие RPC; повторная выдача не меняет имя ученика. Ссылка и токен остаются только в состоянии экрана, в черновик записывается только имя. В демо создаётся локальный ожидающий профиль и явно учебная ссылка на `.invalid`; копирование и отправка такой ссылки отключены. Это намеренное отличие от вебового прототипа: подключение Telegram не симулируется. Удаление такого профиля меняет только данные симулятора.

## Проверки

Сборка Simulator, `ios:check`, `git diff --check` и переносимые XCTest 46/46 прошли. Первый UI-прогон `12-00-41` остановился в проверке даты: системный русский формат использует неразрывный пробел, а регулярное выражение теста ожидало обычный. Проверка уточнена без изменения отображения даты.

Короткий регрессионный тест открытия существующего пополнения прошёл (`13-59-56`). Предыдущие прогоны выявили бесконечное обновление графа SwiftUI при вложенном переходе; оно воспроизводилось даже с минимальной формой без восстановления черновиков. Закрытие профиля и экранов абонемента переведено на системный `presentationMode`, редактирование из истории открывается единым переходом вне строк списка. Полная форма возвращена; временных диагностических флагов нет.

Сквозной демо-сценарий проверяет: исходные 11 занятий → исправление комментария без сдвига даты → удаление пополнения и 3 оставшихся занятия → ошибка нулевого количества → новое пополнение и восстановление 11 занятий → отмена удаления абонемента → создание ожидающего ученика → явное демо-состояние ссылки → отсутствие назначения тренировки → удаление ожидающего профиля.

Сценарий прошёл в светлой и тёмной теме на iPhone 16, iOS 18.3.1 (`14-03-55`, 12 снимков). В первом полном прогоне тест неоднозначно выбирал между двумя кнопками «Удалить ученика»; подтверждению добавлен отдельный accessibility identifier. Повторный прогон проверил фактическое удаление и возврат к списку. Сравнения шести пар экранов: `work/ledger-parity/comparison-{light,dark}.png`. Две числовые строки оплаты выровнены сверху, чтобы ошибка одного поля не сдвигала соседнее. Системное «Поделиться» в рабочем приглашении использует нейтральную вторичную кнопку; основное действие — копирование ссылки.

При accessibility-размерах общей кнопке оставлена полноширинная подпись без дублирующей иконки: длинные слова получают больше места, размер текста и область нажатия не уменьшаются.

Полный сценарий также прошёл на iPhone SE 375 × 667 с максимальным системным размером текста (`14-07-08`): ввод с клавиатуры, ошибки количества, сохранение/удаление оплаты, создание и удаление ожидающего ученика. После визуальной правки подписей общий короткий регрессионный тест дополнен сохранением и возвратом к истории при обычном и максимальном шрифте.

Веб-снимки: `work/ledger-parity/web-{history,payment,new,invite,ready,pending}-{light,dark}.png`. Нативные снимки сохраняются в xcresult с теми же именами без `web-`. Копирование/отправка настоящей ссылки и принятие через реальный Telegram требуют проверки на рабочих аккаунтах; этот этап не выполняет отправку сообщений, не создаёт приглашения и не удаляет данные в Supabase.

Далее — заметки и видео, затем отдельная приёмка сети, истечения сессии и конфликтов с реальными аккаунтами. Визуальная сверка не означает полную готовность всех этих состояний.
