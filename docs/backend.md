# Backend REPPY

## Выбранный стек

- Supabase CLI для локальной разработки и миграций.
- PostgreSQL как источник правды.
- Supabase Data API для обычных предметных операций.
- PostgreSQL RPC для транзакционных и идемпотентных сценариев.
- Supabase Auth для аккаунтов и пользовательских сессий.
- Закрытый Supabase Storage bucket `instruction-videos` для видео тренера.

Авторизованные аккаунты используют `SupabaseRepository`: расписание, тренировки, результаты, абонементы и связи тренер–ученик хранятся в PostgreSQL и обновляются через Realtime. `LocalStorageRepository` остаётся только для публичного демо без Supabase-сессии.

Frontend подключается к Supabase Auth, если заданы `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Без этих переменных приложение запускает изолированный демо-режим. Сессия и роль аккаунта всегда определяются Supabase Auth и неизменяемой записью `profiles`.

## Окружения

| Окружение | Назначение | Данные |
| --- | --- | --- |
| Local | разработка и автоматические проверки | локальный Supabase через Docker |
| Preview | интеграционные и E2E-проверки | отдельный hosted-проект без production-данных |
| Production | рабочее приложение | отдельный hosted-проект с резервным копированием |

Миграции из `supabase/migrations` являются единственным источником схемы для всех окружений. Секреты и `service_role` не сохраняются в репозитории и никогда не передаются браузеру.

## Основная модель

`profiles` содержит аккаунты из `auth.users`. Ученик до регистрации существует в `students` без `account_id`; после принятия приглашения его Auth-профиль привязывается к существующей записи. Связь и все данные конкретного тренера хранятся через `trainer_student_relationships`.

## Регистрация тренера

Создание тренера — доверенная серверная операция. Backend или администратор создаёт Auth-пользователя через Admin API и передаёт:

```ts
{
  user_metadata: {
    display_name: 'Имя тренера',
  },
  app_metadata: {
    reppy_role: 'trainer',
  },
}
```

Триггер `on_auth_user_created` создаёт `profiles` с фиксированной ролью `trainer` только при доверенном `raw_app_meta_data.reppy_role`. Имя берётся из `user_metadata`, обрезается по краям и должно содержать от 2 до 120 символов. Любые значения роли, переданные обычным клиентом через `signUp` в `user_metadata`, игнорируются.

Последующая авторизация опирается на неизменяемую запись `profiles` и RLS, а не на редактируемые пользовательские metadata. Секретный ключ Admin API используется только на доверенном backend и никогда не передаётся frontend.

## Приглашение ученика

Тренер сначала создаёт ученика и связь со статусом `invited`, затем вызывает `create_student_invitation(relationship_id, target_email)`. Сервер нормализует email, генерирует 256-битный одноразовый токен сроком на 48 часов, сохраняет только SHA-256 hash и возвращает исходный токен единственный раз. Повторный выпуск автоматически отзывает предыдущие неиспользованные приглашения этой связи. Частичный unique index дополнительно гарантирует, что у связи не может быть двух открытых приглашений.

Ссылка приглашения передаёт токен frontend-приложению в hash-фрагменте URL, чтобы он не попадал в HTTP Referer и серверные access-логи. До входа `get_student_invitation_preview(token)` возвращает только имя ученика, имя тренера и срок действия. После создания или входа в Auth-аккаунт frontend вызывает `accept_student_invitation(token)`.

Принятие выполняется одной транзакцией:

1. Блокируется связь и проверяется срок, отзыв и предыдущее использование токена.
2. Подтверждённый email Auth-пользователя сравнивается с `target_email` приглашения.
3. Создаётся `profiles` с фиксированной ролью `student` и именем из существующей записи ученика.
4. Auth ID записывается в `students.account_id`.
5. Связь переводится в `active`, а приглашение отмечается принятым.
6. Остальные активные токены этой связи отзываются.

Повтор принятия тем же аккаунтом идемпотентен. Другой аккаунт, тренер с уже существующим профилем, просроченный или отозванный токен получают одинаковый отказ без раскрытия состояния приглашения. Тренер отзывает неиспользованный токен через `revoke_student_invitation(invitation_id)`.

Назначения и сессии сохраняют независимые `workout_snapshot` в `jsonb`. Результаты подходов остаются реляционными и ссылаются на `exercise_definitions`, чтобы прогрессию можно было строить обычным SQL-запросом.

Журнал `subscription_entries` хранит пополнения, списания и возвраты. Уникальность `(session_id, kind)` не позволяет повторно списать или вернуть одно занятие. Ученик получает только баланс и три последних пополнения через `get_subscription_summary`; полный журнал доступен тренеру.

Видео лежат в приватном bucket по пути:

```text
<relationship_uuid>/<video_uuid>/<file-name>
```

Политики Storage разрешают запись тренеру и чтение обоим участникам связи.

## Серверные операции первой миграции

- `create_student_invitation(relationship_id, target_email)` — выпускает привязанный к email токен и отзывает прежние активные приглашения связи.
- `get_student_invitation_preview(token)` — показывает безопасный preview владельцу ссылки без входа.
- `accept_student_invitation(token)` — атомарно создаёт профиль ученика, привязывает Auth-аккаунт и активирует связь.
- `revoke_student_invitation(invitation_id)` — идемпотентно отзывает неиспользованный токен.
- `start_workout_session(assignment_id)` — идемпотентно создаёт сессию из снимка назначения.
- `save_session_progress(session_id, expected_revision, workout_snapshot, results)` — одной транзакцией проверяет снимок и полный набор подходов, заменяет результаты и повышает `revision`. Устаревшая версия получает конфликт вместо молчаливой перезаписи.
- `complete_workout_session(session_id, charge_subscription)` — завершает сессию, обновляет назначение и при необходимости списывает занятие одной транзакцией. Ученик не может отказаться от списания.
- `archive_workout_session(session_id)` — скрывает завершённую сессию и назначение, создавая возврат при наличии списания.
- `get_subscription_summary(relationship_id)` — безопасно возвращает ученику баланс и последние пополнения без доступа к полному журналу.

Прямые `insert`, `update` и `delete` для `set_results` закрыты: запись выполняется только через `save_session_progress`. Завершённые назначения нельзя редактировать через Data API. Повтор назначения обязан ссылаться на неудалённое назначение в той же связи, а первый сегмент `object_path` видео обязан совпадать с `relationship_id`.

RLS-тесты проверяют все десять публичных таблиц от имени ученика, его тренера и постороннего тренера; роль `anon` не имеет прямых прав на таблицы. Новые таблицы и функции по умолчанию не получают права `anon` и `authenticated` — необходимые разрешения выдаются явно в миграции.

## Локальная разработка

Для локального стека нужен запущенный Docker-совместимый runtime.

```bash
npm run supabase:start
npm run db:reset
npm run db:lint
npm run db:test
```

Создайте локальный файл окружения из примера и подставьте значения, которые выводит `supabase status`:

```bash
cp .env.example .env.local
```

Для hosted-проекта те же публичные значения находятся в диалоге Connect или Supabase Dashboard → Settings → API Keys. `service_role` в `.env.local` добавлять нельзя. В Auth → URL Configuration добавьте адрес приложения в `Site URL` и в список разрешённых Redirect URLs. Поток авторизации использует PKCE; подтверждение email ученика возвращает его на исходную ссылку приглашения.

Для GitHub Pages добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` как Repository variables в Settings → Secrets and variables → Actions → Variables. Workflow передаёт их только финальной production-сборке; E2E по-прежнему проверяет изолированный демо-режим.

## Серверная доставка Telegram

Триггеры базы записывают события в `telegram_notification_outbox`. Edge Function `telegram-notifications` умеет обрабатывать очередь двумя способами:

- сразу после пользовательского действия — авторизованным запросом приложения;
- независимо от браузера — заданием Supabase Cron каждые 30 секунд.

Периодический вызов использует `pg_cron`, `pg_net` и значения из Supabase Vault. После применения миграций и деплоя функции выполните один раз в SQL Editor под администратором проекта:

```sql
select public.configure_telegram_notification_delivery(
  'https://PROJECT_REF.supabase.co',
  'YOUR_PUBLISHABLE_KEY'
);
```

Publishable key допустимо использовать для этого вызова: функция сверяет его с ключами текущего Supabase-проекта, не возвращает содержимое очереди и выполняет только идемпотентную доставку уже созданных сервером событий. Таблица outbox и claim/finalize RPC недоступны ролям `anon` и `authenticated`.

Первичное подключение hosted-проекта и применение миграций:

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push --dry-run
npx supabase db push
```

Не используйте `--include-seed` для production. После применения миграции создайте первого тренера доверенной Admin API операцией:

```bash
cp .env.admin.example .env.admin.local
npm run trainer:create
```

В `.env.admin.local` должны находиться URL проекта, server-only `service_role`/secret key и данные первого тренера. Файл игнорируется Git. Скрипт передаёт роль через защищённый `app_metadata`, поэтому триггер миграции создаёт профиль тренера; обычная браузерная регистрация не может назначить себе эту роль.

Остановить локальные сервисы:

```bash
npm run supabase:stop
```
