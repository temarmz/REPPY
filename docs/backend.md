# Backend REPPY

## Выбранный стек

- Supabase CLI для локальной разработки и миграций.
- PostgreSQL как источник правды.
- Supabase Data API для обычных предметных операций.
- PostgreSQL RPC для транзакционных и идемпотентных сценариев.
- Supabase Auth для аккаунтов и пользовательских сессий.
- Закрытый Supabase Storage bucket `instruction-videos` для видео тренера.

Авторизованные аккаунты используют `SupabaseRepository`: расписание, тренировки, результаты, абонементы и связи тренер–ученик хранятся в PostgreSQL и обновляются через Realtime. `LocalStorageRepository` остаётся только для публичного демо без Supabase-сессии.

Frontend подключается к Supabase Auth, если заданы `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Без этих переменных приложение запускает изолированный демо-режим. Сессия и роль аккаунта всегда определяются Supabase Auth и неизменяемой записью `profiles`.

## Окружения

| Окружение | Назначение | Данные |
| --- | --- | --- |
| Local | разработка и автоматические проверки | локальный Supabase через Docker |
| Preview | интеграционные и E2E-проверки | отдельный hosted-проект без production-данных |
| Production | рабочее приложение | hosted-проект; политика резервного копирования и проверка восстановления ещё настраиваются |

Миграции из `supabase/migrations` являются единственным источником схемы для всех окружений. Секреты и `service_role` не сохраняются в репозитории и никогда не передаются браузеру.

## Основная модель

`profiles` содержит аккаунты из `auth.users`. Ученик до регистрации существует в `students` без `account_id`; после принятия приглашения его Auth-профиль привязывается к существующей записи. Связь и все данные конкретного тренера хранятся через `trainer_student_relationships`.

## Регистрация и вход тренера

Основной публичный сценарий работает только через Telegram OpenID Connect:

1. Пользователь на лендинге нажимает «Войти», а затем выбирает вход или создание кабинета тренера.
2. Telegram подтверждает личность. Имя из Telegram автоматически подставляется в форму и при необходимости редактируется до завершения регистрации.
3. Edge Function `telegram-auth` проверяет ID token, nonce и лимит запросов, создаёт Auth-пользователя с внутренним техническим email, профиль с фиксированной ролью `trainer` и запись `telegram_accounts`.
4. Frontend получает Supabase-сессию и открывает кабинет. При следующих входах тот же Telegram сразу восстанавливает существующий аккаунт.

Пользователь не задаёт email или пароль REPPY. Один Telegram ID нельзя связать с двумя профилями. Отмена Telegram-входа, превышение лимита, повторная привязка и некорректный ответ провайдера возвращают отдельные безопасные ошибки без создания частичного профиля.

Старый операторский сценарий с `trainer:invite`, email и паролем оставлен в кодовой базе только для совместимости и аварийных операций. Он не является текущим пользовательским onboarding и должен быть удалён после завершения миграции.

Доверенная Admin API операция создаёт Auth-пользователя и передаёт:

```ts
{
  user_metadata: {
    display_name: 'Имя тренера',
  },
  app_metadata: {
    reppy_role: 'trainer',
  },
}
```

Триггер `on_auth_user_created` создаёт `profiles` с фиксированной ролью `trainer` только при доверенном `raw_app_meta_data.reppy_role`. Имя берётся из `user_metadata`, обрезается по краям и должно содержать от 2 до 120 символов. Любые значения роли, переданные обычным клиентом через `signUp` в `user_metadata`, игнорируются.

Последующая авторизация опирается на неизменяемую запись `profiles` и RLS, а не на редактируемые пользовательские metadata. Секретный ключ Admin API используется только на доверенном backend и никогда не передаётся frontend.

## Приглашение ученика

Тренер создаёт ученика и одноразовую ссылку приглашения сроком на 48 часов. Сервер хранит только SHA-256 hash токена; повторный выпуск отзывает предыдущую открытую ссылку этой связи. Токен находится в hash-маршруте приложения и не попадает в HTTP Referer.

Ученик открывает ссылку и подтверждает вход через Telegram. Edge Function `telegram-auth` проверяет Telegram ID token и вызывает `accept_student_invitation_from_telegram(...)`. Одна транзакция:

1. блокирует приглашение и проверяет срок, отзыв и предыдущее использование;
2. создаёт Supabase Auth-пользователя с внутренним техническим email и профиль с фиксированной ролью `student`;
3. связывает Telegram, профиль, запись ученика и связь с тренером;
4. активирует связь, помечает приглашение использованным и отзывает остальные открытые токены.

Ученик не задаёт email или пароль. Просроченное, отозванное, уже использованное приглашение и Telegram, связанный с другим аккаунтом, получают понятные отдельные ошибки. Поле `target_email` пока остаётся в старой схеме и интерфейсе как операционная метка, но в Telegram-only сценарии не подтверждает личность и не используется для входа; его следует убрать отдельной миграцией после удаления legacy-потока.

Назначения и сессии сохраняют независимые `workout_snapshot` в `jsonb`. Результаты подходов остаются реляционными и ссылаются на `exercise_definitions`, чтобы прогрессию можно было строить обычным SQL-запросом.

Журнал `subscription_entries` хранит пополнения, списания и возвраты. Уникальность `(session_id, kind)` не позволяет повторно списать или вернуть одно занятие. Ученик читает собственный баланс и журнал в режиме просмотра. Тренер может исправить или удалить отдельное пополнение и полностью удалить записи абонемента, не затрагивая тренировки и их результаты.

Видео лежат в приватном bucket по пути:

```text
<relationship_uuid>/<video_uuid>/<file-name>
```

Политики Storage разрешают запись тренеру и чтение обоим участникам связи.

## Серверные операции первой миграции

- `create_student_invitation(relationship_id, target_email)` — выпускает привязанный к email токен и отзывает прежние активные приглашения связи.
- `get_student_invitation_preview(token)` — показывает безопасный preview владельцу ссылки без входа.
- `accept_student_invitation(token)` — атомарно создаёт профиль ученика, привязывает Auth-аккаунт и активирует связь.
- `revoke_student_invitation(invitation_id)` — идемпотентно отзывает неиспользованный токен.
- `start_workout_session(assignment_id)` — идемпотентно создаёт сессию из снимка назначения.
- `save_session_progress(session_id, expected_revision, workout_snapshot, results)` — одной транзакцией проверяет снимок и полный набор подходов, заменяет результаты и повышает `revision`. Устаревшая версия получает конфликт вместо молчаливой перезаписи.
- `complete_workout_session(session_id, charge_subscription)` — завершает сессию, обновляет назначение и при необходимости списывает занятие одной транзакцией. Ученик не может отказаться от списания.
- `archive_workout_session(session_id)` — скрывает завершённую сессию и назначение, создавая возврат при наличии списания.
- `get_subscription_summary(relationship_id)` — безопасно возвращает ученику баланс и последние пополнения без доступа к полному журналу.
- `accept_student_invitation_from_telegram(...)` — атомарно создаёт Telegram-only аккаунт ученика и активирует связь.
- `delete_subscription_payment(relationship_id, entry_created_at)` — удаляет выбранное пополнение, сохраняя списания тренировок.
- `delete_subscription(relationship_id)` — удаляет журнал абонемента без удаления тренировок и результатов.

Прямые `insert`, `update` и `delete` для `set_results` закрыты: запись выполняется только через `save_session_progress`. Завершённые назначения нельзя редактировать через Data API. Повтор назначения обязан ссылаться на неудалённое назначение в той же связи, а первый сегмент `object_path` видео обязан совпадать с `relationship_id`.

RLS-тесты проверяют все десять публичных таблиц от имени ученика, его тренера и постороннего тренера; роль `anon` не имеет прямых прав на таблицы. Новые таблицы и функции по умолчанию не получают права `anon` и `authenticated` — необходимые разрешения выдаются явно в миграции.

## Локальная разработка

Для локального стека нужен запущенный Docker-совместимый runtime.

```bash
npm run supabase:start
npm run db:reset
npm run db:lint
npm run db:test
```

Создайте локальный файл окружения из примера и подставьте значения, которые выводит `supabase status`:

```bash
cp .env.example .env.local
```

Для hosted-проекта те же публичные значения находятся в диалоге Connect или Supabase Dashboard → Settings → API Keys. `service_role` в `.env.local` добавлять нельзя. Для Telegram OpenID добавьте точный callback приложения в Redirect URIs и `https://temarmz.github.io` в Trusted Origins в настройках бота. Значения `TELEGRAM_OIDC_CLIENT_ID` и `TELEGRAM_OIDC_CLIENT_SECRET` хранятся только в секретах Edge Functions.

Для GitHub Pages добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` как Repository variables в Settings → Secrets and variables → Actions → Variables. Workflow передаёт их только финальной production-сборке; E2E по-прежнему проверяет изолированный демо-режим.

## Серверная доставка Telegram

Триггеры базы записывают события в `telegram_notification_outbox`. Edge Function `telegram-notifications` умеет обрабатывать очередь двумя способами:

- сразу после пользовательского действия — авторизованным запросом приложения;
- независимо от браузера — заданием Supabase Cron каждые 30 секунд.

Периодический вызов использует `pg_cron`, `pg_net` и значения из Supabase Vault. После применения миграций и деплоя функции выполните один раз в SQL Editor под администратором проекта:

```sql
select public.configure_telegram_notification_delivery(
  'https://PROJECT_REF.supabase.co',
  'YOUR_PUBLISHABLE_KEY'
);
```

Publishable key допустимо использовать для этого вызова: функция сверяет его с ключами текущего Supabase-проекта, не возвращает содержимое очереди и выполняет только идемпотентную доставку уже созданных сервером событий. Таблица outbox и claim/finalize RPC недоступны ролям `anon` и `authenticated`.

## Мониторинг backend и Telegram

Read-only проверка доступна оператору через:

```bash
npm run backend:health
```

Команда использует `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` из локального `.env.admin.local`, проверяет конфигурацию `telegram-auth` и `telegram-notifications`, а также ищет в `telegram_notification_outbox` просроченные, зависшие, исчерпавшие попытки и оставшиеся без Telegram-получателя сообщения. Она ничего не отправляет и не изменяет. При проблеме процесс завершается с ненулевым кодом, поэтому команду можно позднее запускать по расписанию в CI или внешнем мониторинге.

Для диагностики откройте Supabase Dashboard → Edge Functions → Logs и проверьте последние ошибки `telegram_notification_outbox`. Наличие ожидающих сообщений младше пяти минут само по себе не считается сбоем: доставка использует повторные попытки с задержкой.

## Резервное копирование и восстановление

Free Plan не включает автоматические database backups, поэтому REPPY использует ручной логический экспорт по официальной схеме Supabase. Локальный CLI должен быть авторизован и связан с нужным проектом.

```bash
npm run backup:create
npm run backup:verify
```

`backup:create` создаёт каталог `.backups/<timestamp>` с правами только для текущего пользователя. В него входят:

- `roles.sql` — роли и их настройки;
- `schema.sql` — прикладная схема, функции, RLS и права;
- `data.sql` — полный экспорт данных, включая Auth и метаданные Storage;
- `application-data.sql` — переносимый срез `public/private` для локальных restore-drill;
- `storage/` — сами объекты всех Storage buckets;
- `manifest.json` — размеры и SHA-256 каждого файла.

`.backups` исключена из Git. После создания скопируйте весь каталог в зашифрованное хранилище вне рабочего компьютера; локальная копия не защищает от потери или поломки Mac. Значение `REPPY_BACKUP_DIR` позволяет сразу выбрать подключённый зашифрованный диск или синхронизируемую защищённую папку.

Проверка `backup:verify` выбирает последний архив либо принимает путь вторым аргументом и сверяет наличие файлов, размеры и SHA-256. Edge Function secrets не входят в database backup: их перечень и значения нужно хранить отдельно в менеджере паролей (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_OIDC_CLIENT_ID`, `TELEGRAM_OIDC_CLIENT_SECRET`). Код функций и миграции уже находятся в Git.

Полное восстановление выполняйте только в новый пустой Supabase-проект по [официальной инструкции Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Никогда не проверяйте restore поверх production. Для data dump с циклическими внешними ключами на время одной транзакции используется `SET session_replication_role = replica`, как в официальной команде восстановления.

24 сентября 2026 года проведён restore-drill в отдельном локальном Supabase-контейнере. Роли, схема и `application-data.sql` восстановились без ошибок; количество строк во всех 16 прикладных и служебных таблицах совпало с production. Полный `data.sql` сохранён для hosted restore: локальный образ Auth отстаёт от hosted-версии и поэтому не используется для проверки внутренних Auth-таблиц.

Первичное подключение hosted-проекта и применение миграций:

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push --dry-run
npx supabase db push
```

Не используйте `--include-seed` для production. Для аварийного создания технического тренера доверенной Admin API операцией:

```bash
cp .env.admin.example .env.admin.local
npm run trainer:create
```

В `.env.admin.local` должны находиться URL проекта, server-only `service_role`/secret key и данные первого тренера. Файл игнорируется Git. Скрипт передаёт роль через защищённый `app_metadata`, поэтому триггер миграции создаёт профиль тренера; обычная браузерная регистрация не может назначить себе эту роль.

Legacy-команда операторского приглашения сохранена только для совместимости:

```bash
npm run trainer:invite
```

Новый публичный onboarding эту команду не использует.

Для тестового сброса сначала выполните `npm run test-accounts:preview`. Он показывает, какие именно Auth-пользователи и связанные данные будут затронуты. Удаление требует два явных подтверждения: список email в `REPPY_TEST_ACCOUNT_EMAILS` и значение `REPPY_CONFIRM_TEST_RESET=DELETE`, после чего запускается `npm run test-accounts:delete`.

Остановить локальные сервисы:

```bash
npm run supabase:stop
```
