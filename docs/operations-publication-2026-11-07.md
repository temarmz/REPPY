- [Возврат на более новую публикацию](https://github.com/temarmz/REPPY/actions/runs/42359842719) также успешен: сайт снова отдаёт release `42357742604-3`.

В production нет демо-входа. Live-проверка не входила в личные аккаунты, не сохраняла тренировки и не выдавала marker localStorage за проверку восстановления настоящего пользовательского черновика. Обе роли, dirty Back/Forward и черновики проверялись полным CI отдельно.

## Найденный дефект повторной публикации

Вторая попытка deploy-job создала второй `github-pages` artifact того же workflow-run. Upload успешен, но deploy-action отказался выбирать один из двух пакетов. Уже опубликованный сайт оставался доступен.

Оба полных release-архива скачаны и проверены по manifest SHA-256. Удалены только два временных Pages-пакета, после чего третья попытка deploy успешна. Полные `reppy-release-*` архивы сохранены. В workflow используются уникальные имена `github-pages-<run>-<attempt>` для upload и deploy; rollback проверяет состояние выбранной попытки, а не последней попытки всего workflow-run. Полный набор браузерных проверок сохраняется; CI использует два независимых worker вместо одного.

## Оставшаяся hosted-проверка

Полное восстановление в новом hosted Supabase-проекте пока не выполнено. В Free-организации заняты оба активных слота production и `reppy-preview-ci`. Для нового изолированного restore-проекта нужна временная пауза только CI-проекта с последующим возвратом либо отдельно согласованный дополнительный ресурс. Рабочий проект не является целью восстановления.

Сценарий hosted restore должен проверить импорт настоящего backup, соответствие числа строк, Auth provisioning/login обеих ролей, RLS, Storage API, тренировку и однократное списание. При нулевом числе исходных видео проверку Storage нужно выполнить на отдельном синтетическом файле и явно отметить это в отчёте.

Локальные отчёты не включают токены/содержимое данных: `work/ops-publication/pages-live-report.json`, `work/ops-publication/edge-production-probe.json`. Архивы и ключи исключены из Git.
