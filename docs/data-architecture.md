# Архитектура данных REPPY

## Текущий поток

```text
React-экраны
  → useReppyData
    → ReppyRepository
      → LocalStorageRepository
```

Компоненты работают только с состоянием `DemoState` и функцией `setData`. Загрузка, миграция, сохранение и очистка находятся за контрактом `ReppyRepository`.

Текущая продуктовая цепочка:

```text
Student
  → Assignment с собственным планом
    → WorkoutSession со снимком выполнения
      → SetResult для каждого подхода
```

Назначение всегда начинается с выбора ученика. Тренер либо собирает новую тренировку, либо копирует одну из предыдущих тренировок этого же ученика и редактирует её. Отдельного общего шаблона и скрытой персональной версии нет.

## Канонические сущности

- `Student` — профиль ученика и ограничения по здоровью.
- `ExerciseDefinition` — элемент библиотеки упражнений с мышечной группой, оборудованием и типом измерения.
- `Assignment` — запланированная тренировка конкретного ученика на локальную дату и время. `workoutSnapshot` является источником правды для плана.
- `WorkoutSession` — начатое или завершённое выполнение назначения. Собственный `workoutSnapshot` фиксирует структуру, которую фактически выполняли и могли менять во время занятия.
- `SetResult` — фактические повторения, вес и состояние отдельного подхода.
- `SubscriptionEntry` — запись журнала пополнения, списания или возврата занятия.

Снимок назначения не зависит от других назначений. Снимок сессии не зависит от последующих изменений назначения. Копирование создаёт новое назначение и новые идентификаторы упражнений, сохраняя `exerciseId` из справочника для построения прогрессии.

## Контракт repository

`ReppyRepository` предоставляет три асинхронные операции:

- `load()` — получить актуальное состояние;
- `save(state)` — сохранить состояние;
- `clear()` — удалить сохранённое состояние.

Асинхронный контракт используется даже для синхронного `localStorage`. Благодаря этому будущий API-адаптер можно подключить к React-хуку без изменения экранов.

## Текущая реализация

`createLocalStorageRepository`:

- читает ключ `reppy-demo-v0`;
- восстанавливает seed при пустом или повреждённом значении;
- применяет `migrateDemoState` к старым версиям, включая перенос старых шаблонов внутрь назначений;
- сериализует состояние только внутри storage-слоя.

Актуальная схема прототипа — `schemaVersion: 5`. Поля `workouts`, `studentWorkoutVersions`, `Assignment.workoutId`, `Assignment.source` и `WorkoutSession.workoutId` поддерживаются только как вход старой миграции и не сохраняются обратно.

## Переход к backend

Первый API-адаптер может реализовать текущий асинхронный контракт, но сохранение целого `DemoState` не должно стать production-протоколом. Для MVP нужны предметные операции:

- загрузить профиль и доступных учеников;
- создать, изменить, перенести и удалить назначение;
- начать, обновить и завершить сессию;
- добавить или исправить запись абонемента;
- создать и принять приглашение;
- читать историю и прогрессию упражнения.

Сервер должен проверять права на каждую операцию. Тренер видит только своих учеников и их данные; ученик — только собственные назначения, сессии, прогрессию и абонемент. Исторический снимок завершённой сессии изменяется только через явно предусмотренную корректировку, а не вследствие редактирования назначения.

## Решения для схемы backend

- Идентификаторы — серверные UUID, клиентские временные ID допустимы только до подтверждения создания.
- `scheduledFor` хранится как календарная дата, `scheduledTime` — как локальное время, а часовой пояс относится к связи с тренером или конкретному назначению.
- События выполнения (`startedAt`, `completedAt`, создание записей журнала) хранятся как UTC timestamps.
- Списание занятия и завершение сессии должны выполняться одной транзакцией и быть идемпотентными.
- Повторная отправка одного завершения не должна создавать второе списание.
- Удаление завершённой тренировки должно одной транзакцией удалить или архивировать результат и создать компенсирующую запись возврата.
- Конфликты одновременного редактирования требуют версии записи (`updatedAt` или revision) и явного ответа API, а не молчаливой перезаписи.

Выбор конкретного backend-провайдера, авторизация, синхронизация конфликтов и серверная база данных относятся к следующему этапу реализации.
